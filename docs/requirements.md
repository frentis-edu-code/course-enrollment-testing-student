# 요구와 합의 규칙

> 학생 시작판의 요구 문서입니다. 규칙, API 계약, 유저스토리와 인수조건까지만 담았습니다. 테스트케이스와 테스트 코드는 실습에서 직접 만듭니다.

이 문서는 예제 앱이 따르는 규칙의 기준입니다. 테스트의 예상 결과는 구현 코드가 아니라 이 문서에서 가져옵니다.
규칙은 수업을 위해 만든 **교육용 가상 규칙**이며 실제 조직의 정책이 아닙니다.

## 1. 입력 메모(다듬기 전)

교육 담당자가 남긴 짧은 요구는 다음과 같은 내용이었습니다.

- 사원이 사내 교육 과정을 온라인으로 신청하고 취소할 수 있어야 한다.
- 과정마다 정원이 있고, 정원이 차면 더 받지 않는다.
- 같은 과정은 한 번만 신청할 수 있다.
- 신청은 마감 전까지, 취소는 교육 시작 하루 전까지 할 수 있다.
- 한 사람이 너무 많은 과정을 한꺼번에 신청하지 못하게 한다.

이 메모에는 모호한 곳이 있어서 아래처럼 질문하고 합의했습니다.

| 번호 | 모호한 곳 | 합의 |
| --- | --- | --- |
| Q1 | 마감 "전까지": 마감 정각도 받는가 | 받는다(R3) |
| Q2 | "한 번만": 취소 뒤 다시 신청할 수 있는가 | 있다. 취소됨 신청은 중복이 아니다(R4) |
| Q3 | 정원을 셀 때 취소한 신청도 세는가 | 세지 않는다. 신청됨만 센다(R6) |
| Q4 | "하루 전": 날짜 기준인가, 24시간인가 | 시작 일시 − 24시간, 그 시각 포함(C3) |
| Q5 | "너무 많은": 몇 개, 취소분 포함인가 | 신청됨 3개까지. 취소됨은 세지 않는다(R5) |
| Q6 | 여러 규칙을 동시에 어기면 무엇을 알리나 | 정해진 순서로 처음 어긴 규칙 하나만(R7) |
| Q7 | 입력 누락, 없는 과정은 | 입력 오류, 과정 없음으로 거절(R1, R2) |

## 2. 용어

- **과정**: 과정 ID, 과정명, 정원, 신청 마감 일시, 시작 일시
- **신청**: 신청 ID, 사원번호, 과정 ID, 상태(`APPLIED` 신청됨 / `CANCELLED` 취소됨)
- **과정의 신청 인원**: 그 과정의 신청 중 신청됨인 것의 수
- **사원의 보유 신청 수**: 그 사원의 신청 중 신청됨인 것의 수(과정 무관)
- **잔여석** = 정원 − 과정의 신청 인원
- **요청 시각**: 서버가 요청을 처리하는 순간의 시각. Asia/Seoul 기준, **초 단위**로 비교합니다(초 미만은 버림). 시계를 주입해 테스트에서 정할 수 있습니다.

## 3. 신청 규칙

| 규칙 | 내용 | 거절 응답 | 메시지 |
| --- | --- | --- | --- |
| R1 필수 입력 | 사원번호와 과정 ID가 모두 있어야 한다. null, 빈 문자열, 공백뿐인 문자열은 누락 | 400 `MISSING_FIELD` | 필수 정보를 입력해 주세요. |
| R2 과정 존재 | 과정 ID의 과정이 있어야 한다 | 404 `COURSE_NOT_FOUND` | 존재하지 않는 과정입니다. |
| R3 신청 마감 | 요청 시각 ≤ 신청 마감 일시 | 409 `ENROLLMENT_CLOSED` | 신청 기간이 지났습니다. |
| R4 중복 금지 | 같은 사원·같은 과정의 신청됨 신청이 없어야 한다(취소됨은 무관) | 409 `DUPLICATE_ENROLLMENT` | 이미 신청한 과정입니다. |
| R5 개인 한도 | 사원의 보유 신청 수 < 3 | 409 `ENROLLMENT_LIMIT` | 동시에 신청할 수 있는 과정은 최대 3개입니다. |
| R6 정원 | 과정의 신청 인원 < 정원 | 409 `COURSE_FULL` | 정원이 마감되었습니다. |
| R7 확인 순서 | R1 → R2 → R3 → R4 → R5 → R6. 처음 어긴 규칙 하나만 응답 | — | — |
| 성공 | 신청됨 상태의 **새 신청**을 만든다. 신청 인원 +1, 잔여석 −1 | 201 | 신청이 완료되었습니다. |

거절되면 데이터는 바뀌지 않습니다(신청이 생기지 않고 신청 인원도 그대로).

## 4. 취소 규칙

| 규칙 | 내용 | 거절 응답 | 메시지 |
| --- | --- | --- | --- |
| C1 신청 존재 | 신청 ID의 신청이 있어야 한다 | 404 `ENROLLMENT_NOT_FOUND` | 신청 내역을 찾을 수 없습니다. |
| C2 상태 | 신청됨이어야 한다 | 409 `ALREADY_CANCELLED` | 이미 취소된 신청입니다. |
| C3 취소 기한 | 요청 시각 ≤ 시작 일시 − 24시간 | 409 `CANCEL_CLOSED` | 취소 가능 기간이 지났습니다. |
| C4 확인 순서 | C1 → C2 → C3 | — | — |
| 성공 | 상태를 취소됨으로 바꾼다. 좌석 즉시 반환(신청 인원 −1), 보유 신청 수 −1 | 200 | 취소가 완료되었습니다. |

취소한 뒤 다시 신청하면 예전 신청을 되살리지 않고 **새 신청 ID**를 만듭니다. 이때 R1~R7을 처음부터 다시 적용합니다.

## 5. API 계약(교육용)

```
GET  /api/courses
  200 [ { "courseId":"C-101", "title":"테스트 설계 기초", "capacity":20, "appliedCount":0,
          "remainingSeats":20, "enrollmentDeadline":"2026-12-01T18:00:00+09:00",
          "startAt":"2026-12-03T09:00:00+09:00", "cancelDeadline":"2026-12-02T09:00:00+09:00" }, ... ]

POST /api/enrollments            본문 { "employeeId": "E1001", "courseId": "C-101" }
  201 { "enrollmentId": 501, "courseId": "C-101", "status": "APPLIED" }
  4xx { "code": "COURSE_FULL", "message": "정원이 마감되었습니다." }

POST /api/enrollments/{enrollmentId}/cancel   (본문 없음)
  200 { "enrollmentId": 501, "status": "CANCELLED" }
  4xx { "code": "CANCEL_CLOSED", "message": "취소 가능 기간이 지났습니다." }

GET  /api/enrollments?employeeId=E1001        내 신청 목록(취소됨 포함, 신청 ID 순)
  200 [ { "enrollmentId": 501, "courseId": "C-101", "courseTitle": "테스트 설계 기초", "status": "APPLIED" } ]

GET  /api/lab-info                            실습 정보
  200 { "appId": "course-enrollment-testing", "notice": "...", "clockMode": "FIXED",
        "labNow": "2026-11-20T10:00:00+09:00", "timeZone": "Asia/Seoul", "resetMethod": "..." }
```

상태코드는 팀이 합의한 계약입니다. 현재 상태와 충돌해 거절하는 경우(마감, 중복, 한도, 정원, 취소 상태·기한)는 409, 클라이언트 입력 오류는 400을 씁니다(RFC 9110의 409, 400 정의 참고). 다른 팀은 다른 코드를 고를 수 있으므로 테스트의 예상값은 이 계약에서 가져옵니다.

## 6. 화면(교육용 가정)

- 과정 목록: 과정명, 정원, 잔여석, `신청` 버튼. 잔여석 0이면 `정원 마감` 표시와 버튼 비활성. 그래도 서버는 R6을 다시 확인합니다.
- 결과 메시지: 3·4절의 메시지를 화면 위쪽 알림 영역에 보여 줍니다(서버가 준 메시지를 그대로 씀).
- 내 신청 목록: 과정명, 상태(신청됨/취소됨), `취소` 버튼. 누르면 "정말 취소하시겠습니까?" 확인 창이 뜨고, 확인해야 취소를 요청합니다.
- 실습 기준 시각과 "교육용, 인증·권한 없음" 안내를 화면 위쪽에 표시합니다.

## 7. 기준 데이터(시드)

서버를 시작할 때마다 아래 4개 과정이 들어갑니다(시각은 Asia/Seoul).

| 과정 ID | 과정명 | 정원 | 신청 마감 일시 | 시작 일시 | 취소 기한(C3) |
| --- | --- | --- | --- | --- | --- |
| C-101 | 테스트 설계 기초 | 20 | 2026-12-01 18:00:00 | 2026-12-03 09:00:00 | 2026-12-02 09:00:00 |
| C-102 | API 테스트 실무 | 20 | 2026-12-08 18:00:00 | 2026-12-10 09:00:00 | 2026-12-09 09:00:00 |
| C-103 | 화면 테스트 입문 | 20 | 2026-12-15 18:00:00 | 2026-12-17 09:00:00 | 2026-12-16 09:00:00 |
| C-104 | 회귀 테스트 운영 | 20 | 2026-12-22 18:00:00 | 2026-12-24 09:00:00 | 2026-12-23 09:00:00 |

**기본 시드에는 신청이 없습니다.** 모든 과정이 잔여석 20으로 시작합니다. 테스트에 필요한 신청 상태(예: "C-101 신청 인원 20")는 각 테스트가 따로 만듭니다. 사원번호는 `E1001`~`E1030`을 씁니다.

## 8. 이 예제에서 추가로 정한 것

위 규칙에 없는 부분은 아래처럼 정했습니다. 수업에서 "규칙 밖의 결정"으로 다룰 수 있습니다.

| 항목 | 결정 |
| --- | --- |
| 깨진 JSON, 본문 없음, 필드 타입 불일치 | 400 `INVALID_REQUEST` "요청 형식이 올바르지 않습니다." (R1의 `MISSING_FIELD`와 구분) |
| 빈 객체 `{}`, 필드 누락 | R1에 해당하므로 400 `MISSING_FIELD` |
| 숫자가 아니거나 범위를 넘는 신청 ID(`/api/enrollments/abc/cancel`) | 400 `INVALID_REQUEST` |
| JSON이 아닌 Content-Type | 415 `UNSUPPORTED_MEDIA_TYPE` |
| 없는 주소, 허용하지 않는 메서드, 예상하지 못한 서버 오류 | 404 `NOT_FOUND`, 405 `METHOD_NOT_ALLOWED`, 500 `INTERNAL_ERROR` |
| 오류 응답에 내부 정보 | 넣지 않는다. 언제나 `{code, message}`만 돌려준다 |
| 사원 존재 확인 | **하지 않는다.** 사원 목록이 없으므로 비어 있지 않은 사원번호는 모두 받는다 |
| 사원번호 길이 | 길이 규칙 없음. 저장 열도 H2 VARCHAR 최대 길이(1,000,000,000자)라 51자 이상도 그대로 받는다 |
| 앞뒤 공백 | 사원번호·과정 ID의 앞뒤 공백은 잘라서 같은 값으로 본다(`" E1001 "` = `"E1001"`) |
| 내 신청 목록에서 사원번호 누락 | 400 `MISSING_FIELD` |
| 요청 시각의 초 미만 | 버린다. 18:00:00.900은 18:00:00으로 보고 접수 |
| 신청 ID | 501부터 1씩 늘어난다. 의미 있는 값이 아니며 테스트는 특정 ID에 기대지 않는다 |
| 동시 요청 | 같은 서버 안에서 신청·취소를 한 번에 하나씩 처리한다. 여러 서버에 걸친 보장은 하지 않는다 |

## 9. 유저스토리와 인수조건

인수조건은 업무 담당·개발·테스트가 함께 합의한 "이 스토리를 받아들일 조건"입니다. 3·4절 규칙을 업무 말로 다시 적은 것이며, 새 규칙을 더하지 않습니다.

### US-1 교육 과정 신청

> 사원으로서 원하는 교육 과정을 온라인으로 신청하고 싶다. 그래야 자리를 미리 확보하고 일정을 세울 수 있다.

| ID | 인수조건 | 근거 |
| --- | --- | --- |
| AC1-1 | 다른 신청 규칙을 모두 지킨 사원이 마감 일시까지 정원에 여유가 있는 과정을 신청하면 접수되고 잔여석이 1 줄어든다 | R3, R6, 성공 |
| AC1-2 | 정원이 찬 과정은 신청할 수 없고, 정원이 마감되었다는 안내를 받는다 | R6 |
| AC1-3 | 이미 신청한 과정은 다시 신청할 수 없다. 취소한 과정은 다시 신청할 수 있다 | R4 |
| AC1-4 | 신청 마감 일시가 지나면 신청할 수 없다. 마감 정각까지는 신청할 수 있다 | R3 |
| AC1-5 | 신청됨 상태의 과정을 3개 가진 사원은 다른 과정을 신청할 수 없다 | R5 |
| AC1-6 | 신청할 수 없을 때는 이유를 하나 알려 준다. 이유가 여럿이면 정해진 순서(R7)의 첫 번째를 알려 준다 | R7 |

### US-2 신청 취소

> 사원으로서 신청한 과정을 취소하고 싶다. 그래야 참석할 수 없을 때 자리를 다른 사람에게 돌려줄 수 있다.

| ID | 인수조건 | 근거 |
| --- | --- | --- |
| AC2-1 | 과정 시작 24시간 전 시각까지 신청됨 상태의 신청을 취소할 수 있다. 그 시각 정각도 포함한다 | C2, C3 |
| AC2-2 | 취소하면 좌석이 바로 반환된다. 다른 사원이 다른 신청 규칙을 지키면 그 자리에 신청할 수 있다 | 취소 성공 |
| AC2-3 | 이미 취소한 신청은 다시 취소할 수 없다 | C2 |
| AC2-4 | 취소 기한이 지나면 취소할 수 없고 그 이유를 안내받는다 | C3 |

인수조건을 확인하는 자동 테스트가 모두 통과해도 그것이 곧 사용자의 인수 승인은 아닙니다. 승인은 업무 담당자가 테스트 결과와 남은 위험을 보고 내립니다.
