# 실습 진행 안내

## 시작할 때

학생 저장소: https://github.com/frentis-edu-code/course-enrollment-testing-student · 전체 받기와 준비는 README를 따릅니다. 이 폴더는 학생 시작판입니다. 앱·테스트 틀·도구 설정은 원본과 같습니다. `docs/AI-요청문.md`가 이번 수업의 복사용 정본입니다. 옛 `docs/worksheets/`의 양식과 요청은 참고이며, 먼저 채울 필요가 없습니다.

저장소의 파일을 읽고 허용한 파일에 쓰며 명령을 실행할 수 있는 AI 도구에서 이 프로젝트 루트를 엽니다. 읽기 전용 챗봇이라면 필요한 파일 내용을 직접 입력하고, 저장과 실행은 본인 터미널에서 합니다. 앱·support·요구·설정·의존성 변경은 허용하지 않습니다. 준비가 없으면 설치·설정 변경으로 우회하지 말고 강사에게 알립니다.

AI 요청 → 생성 파일의 근거·확인 범위 검토 → 실행 원문 확인 순서로 진행합니다. 새 Java 테스트는 `practice` 아래 `*Test.java`로 이름 짓고 해당 JUnit 태그를 붙입니다. 태그만으로 탐색·실행을 보장하지 않습니다. 신규 테스트 이름과 실행 수가 0이 아닌지, 실패·오류·건너뜀을 실제 출력에서 확인합니다.

## 실습별로 읽고 만들 것

파일을 AI에 직접 읽힐 수 있으면 아래 파일을 지정합니다. 채팅만 가능하면 해당 절과 파일 내용을 붙여 넣습니다. 먼저 빈 양식을 채우지 않습니다.

| 실습과 목적 | 읽을 실제 파일 | AI에 요청할 것 | 생성 결과에서 볼 것 → 실행·판단 |
| --- | --- | --- | --- |
| 1. 신청·취소의 확인 지점 찾기 | `docs/requirements.md` | 확인할 상황과 근거 | 항목 하나를 규칙과 비교하고 먼저 볼 이유 설명. 코드 실행 없음 |
| 2. 마감의 양쪽 결과 설계 | `docs/requirements.md` Q1·R3·7절 C-101·AC1-4 | 사전 상태·입력·예상 결과 표 | 정각 접수 / 1초 뒤 거절·데이터 불변의 근거 확인. 앱 실행 없음 |
| 3. 정원 규칙 단위 검사 | 아래 경로의 `EnrollmentRules.java`, `EnrollmentCheck.java`, `RulesPracticeTest.java`와 요구 3절 | 정원 20에 인원 19·20의 JUnit 테스트 | 규칙 객체만 호출하는지 읽기 → 루트 `./mvnw test -Dgroups=unit` → 신규 이름·실행 수·건너뜀 확인 |
| TDD. 취소 기한 새 기능 | 요구 4절 C3와 아래 종료 관문 | practice의 새 클래스·실패 테스트 | 정각·1초 뒤 검증을 읽기 → 빨강·초록·정리 때 같은 unit 명령 |
| 4 API. 취소한 좌석 반환 | `ApiTestSupport.java`, `TestData.java`, `ApiPracticeTest.java`와 요구 3~5·9절 | 정원 준비 → 취소 → 다른 사원 신청의 MockMvc 테스트 | 응답·인원·잔여석 검증 읽기 → 루트 `./mvnw test -Dgroups=api` |
| 4 화면. React 신청·취소 | `frontend/e2e/practice-flow.spec.js`, `frontend/e2e/helpers.js`, `frontend/playwright.config.js`와 요구 4~6절 | 저장해서 재실행할 Playwright 테스트 | 확인 창·목록 대기·안내·상태·잔여석 읽기 → `frontend`에서 `npm run e2e` |
| 5. 변경 영향과 회귀 | 루트 `lab5-change.patch`, 요구 3·4·9절, 현재 practice 테스트 | 먼저 영향 분석만 | 변경·규칙·실제 존재하는 테스트 대조 → 아래 기준선·패치·재검증 순서 |
| 5 보고. 실제 근거 정리 | 직접 얻은 터미널 출력 또는 `target/surefire-reports/`, 직접 확인 기록, 영향 분석 | 먼저 근거표만 | 원문 대조 → 확인한 표를 새 입력으로 보고 요청. 없는 결과는 미실행 |

### Java 테스트 공통 조건

- `rules`의 정확한 경로는 `src/main/java/com/example/enrollment/rules/`입니다. `EnrollmentRules.java`와 입력 자료형 `EnrollmentCheck.java`를 여기서 읽습니다.
- `practice`와 `support`는 `src/test/java/com/example/enrollment/` 아래입니다. `ApiTestSupport.java`·`TestData.java`는 support, `RulesPracticeTest.java`·`ApiPracticeTest.java`는 practice에 있습니다.
- 생성 도구는 JUnit 5·AssertJ입니다. 새 테스트 파일은 `*Test.java`, 규칙/TDD는 `@Tag("unit")`, API는 `@Tag("api")`를 사용합니다. 기존 틀을 쓸 때만 해당 틀의 `@Disabled`와 미작성 `fail`을 실제 검증으로 바꿉니다. 기존 테스트를 끄거나 실패를 숨기지 않습니다.
- 규칙 단위 검사는 Spring·DB 없이 `new EnrollmentRules()`를 호출하고 고정 시각을 씁니다. API 검사는 `ApiTestSupport`로 Spring 컨텍스트·MockMvc·DB를 연결하며 실제 HTTP 서버를 띄우지 않습니다. React 화면 E2E와 다른 범위입니다.
- 변경은 practice 테스트만 허용합니다(TDD의 새 연습 클래스도 practice). 앱·support·요구·설정·의존성을 바꾸지 않습니다. 단원 5의 제품 수정은 아래 작업 사본의 제한된 절차만 예외입니다. 설치가 필요하면 멈추고 강사에게 알립니다.
- AI가 만든 코드를 먼저 검토하고 위 명령을 실행합니다. AI 실행 기능이 없으면 본인 터미널에서 실행합니다. Windows는 `./mvnw` 대신 `.\\mvnw.cmd`를 씁니다. 통과·실패·오류·건너뜀과 신규 테스트 이름·실행 수를 실제 출력으로 판단합니다.

## TDD 종료 관문

1. **빨강:** 신규 테스트 이름과 의도한 실패 이유를 식별합니다. 기존 실패나 문법·환경 오류는 이번 빨강의 증거가 아닙니다.
2. **초록:** 테스트 예상값은 유지하고, 새 연습 클래스의 최소 구현만 AI에게 요청한 뒤 같은 `./mvnw test -Dgroups=unit`을 실행합니다.
3. **정리:** 동작을 바꾸지 않는 정리를 요청하고 같은 명령으로 재통과를 확인합니다. 정리할 것이 없어 유지해도 다시 실행합니다.
4. 미완료라면 새 연습 클래스와 테스트만 프로젝트 밖에 별도 보관한 뒤 작업 폴더에서 제거합니다. 파일명·실패 원인·미실행 단계를 기록하고 기존 테스트는 끄지 않습니다. 후속 전체 실행에 의도한 빨강을 섞거나 건너뜀을 통과로 세지 않습니다. 가능하면 시작 사본을 따로 두고 TDD를 진행합니다.

## 경계·예외·조합과 짧은 판단

정원 20에서 인원 10은 정상 대표값, 19·20은 접수와 거절이 갈리는 경계입니다. 이미 21인 상태에서도 정원 마감인지 보는 것은 예외 보강의 예이고, 중복이며 정원도 찬 경우 먼저 알릴 거절 사유를 보는 것은 조합의 예입니다. 예상값은 요구 문서의 규칙·확인 순서에서 정합니다.

생성 결과가 어느 방향을 확인하고 무엇을 남겼는지 한 항목만 설명합니다. 실제로 부족한 방향 하나가 있으면 이유와 함께 AI에게 보강을 요청하고 실행합니다. 모든 방향을 별도 과제로 만들거나 타당한 테스트에 무조건 수정을 강요하지 않습니다. 전체 방향의 독립 수행·숙달을 이 짧은 확인으로 판정하지 않습니다.

추적성은 근거가 없는 케이스·케이스가 없는 규칙 중 하나를 찾는 질문으로 확인합니다. 결정표는 조건 조합과 거절 순서, 상태전이는 취소 후 재신청과 기존 이력의 관계를 비교합니다. 마감만 요청한 결과에 다른 범위가 없다는 이유만으로 오답이라 하지 않습니다. 화면 안내문은 E2E에서, 반환된 좌석과 후속 신청은 API 연결에서 볼 수 있는 이유를 한 항목으로 설명합니다.

## 화면 E2E

`window.confirm`은 화면의 DOM 버튼이 아닙니다. 취소 클릭 전에 dialog 처리기를 등록하고 문구를 확인한 뒤 `accept`해야 합니다. 취소 후 상태·메시지·잔여석을 확인합니다. 사원번호 표시만으로 목록 응답이 끝났다고 판단하지 말고, 기대한 목록과 상태를 조건으로 기다립니다. 고정 초 대기를 성공 근거로 쓰지 않습니다.

브라우저 컨텍스트 격리는 서버 DB 초기화가 아닙니다. 새 서버·빈 데이터로 대표 한 흐름을 확인하는 경우와 여러 테스트·기존 서버를 쓰는 경우를 구분하고, 각 테스트의 사전 데이터·정리 방법을 확인합니다. Maven 전체 테스트는 Playwright를 실행하지 않습니다. 화면 테스트는 `frontend`에서 `npm run e2e`로 별도 실행합니다.

## 단원 5: 분석·기준선·패치·재검증

강사 시연 또는 수업에서 허용한 **작업 사본**에서만 수행합니다. 원래 학생판·강사 기준판은 보존합니다. `lab5-change.patch`는 이 프로젝트 루트에 있습니다. 패치를 읽고 분석하는 것과 실제 적용은 구분합니다.

1. AI 첫 요청은 **영향 분석만** 합니다. 패치와 요구 3·4·9절을 사람이 대조하고, 아직 테스트가 없는 범위도 표시합니다.
2. 대표 재신청 테스트를 `practice`의 `*Test.java`·`@Tag("api")`로 만들도록 요청합니다. 요구 R4·AC1-3에서 예상값을 정하고, **패치 적용 전** 같은 테스트를 실행해 기준선을 남깁니다. 기존 실패가 있으면 먼저 구분합니다.
3. 프로젝트 루트에서 패치를 적용하고 같은 테스트를 다시 실행합니다.

```bash
patch -p1 < lab5-change.patch
./mvnw test -Dgroups=api
```

`patch` 도구가 없는 Windows 등에서는 여기서 멈추고 강사에게 준비된 작업 사본을 요청합니다. 임의 설치나 다른 방식으로 소스를 고쳐 적용했다고 하지 않습니다. 패치가 이미 적용됐거나 문맥이 다르면 중복 적용하지 않습니다.

4. 실패하면 요구·테스트·환경/데이터·제품 중 원인을 판별합니다. 제품 결함으로 판단한 경우에만 `EnrollmentRepository.java`의 조회 조건 하나로 수정 범위를 제한해 AI에 요청합니다. 테스트 예상값을 현재 동작에 맞춰 바꾸지 않습니다. **본 안내는 수행 제안이며 새 AI 생성·수정·시험의 실행 증거가 아닙니다.**
5. 실패했던 동일 테스트를 재실행하고, 선택 묶음과 전체를 실행해 결과를 각각 기록합니다.

```bash
./mvnw test -Dgroups=unit,api,acceptance
./mvnw test
```

R4의 같은 사원 재신청 한 건으로 R5의 개인 한도에서 취소분 제외까지 확인했다고 쓰지 않습니다. R5는 신청됨 2건·취소됨 1건을 가진 사원이 다른 과정을 신청하는 등의 별도 확인 범위입니다. 이번에 실행하지 못하면 남은 위험으로 남깁니다.

### 직접 화면·Swagger로 비교할 때

예전 jar는 변경 소스의 검증 대상이 아닙니다. 위 테스트 실패를 먼저 해결하거나 패치를 복구해 기준 상태의 통과를 확인한 뒤 `./mvnw clean package`로 새 jar를 만듭니다. 실패 테스트를 숨기는 skip 옵션으로 빌드하지 않습니다. 이전 서버를 종료하고 새 `target/course-enrollment-testing-0.1.0.jar`를 기동했는지 확인합니다. React 빌드가 필요하면 README의 `npm ci`·`npm run build` 준비 절차를 따릅니다. 실패 때문에 재빌드할 수 없으면 직접 확인은 미실행으로 기록합니다.

### 복구

패치만 적용했고 이후 조회 파일을 별도로 고치지 않은 사본은 다음으로 되돌린 뒤 파일 내용과 대표 테스트 결과를 기준선과 비교합니다.

```bash
patch -R -p1 < lab5-change.patch
```

AI 수정까지 했다면 역패치가 맞지 않을 수 있으므로 강사와 확인하고 패치 전 보관 사본의 해당 파일로 복구합니다. `git reset` 등으로 다른 작업을 지우지 않습니다. 복구와 복구 뒤 실행 여부도 기록합니다.

## 근거표를 확인한 뒤 보고 요청

먼저 실제 실행 원문으로 근거표만 생성시킵니다. 사람이 기록 위치·테스트 이름·숫자·예상/실제·결과 종류를 원문과 대조하고 틀린 행을 고칩니다. **그 확인이 끝난 표를 새 입력으로 주기 전에는 보고 초안을 요청하지 않습니다.** 확인한 표로 범위 → 규칙·위험별 결과 → 발견한 결함 → 미확인과 남은 위험 → 다음 조치를 요청합니다. 보고도 원인 추정과 업무 담당자의 배포·인수 결정을 구분해 다시 읽습니다. 기록이 없으면 결과를 만들지 않고 미실행으로 남깁니다.

## 준비와 미검증 범위

JDK 21, README의 Node 버전, Maven/npm 의존성, 새 jar와 Chromium, `patch` 도구 준비를 수업 전에 확인합니다. wrapper 설정·lockfile·React 진입점/api·OpenAPI 문서는 이 후보에 포함돼 있습니다. 파일 존재 확인은 설치·빌드·AI 생성·테스트 성공을 뜻하지 않습니다. 이 개정에서는 새 AI 요청 실행, Maven/Playwright, 패치 적용·복구, jar 빌드·기동, 학생 성취와 시간 리허설을 수행하지 않았습니다.
